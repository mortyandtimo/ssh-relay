# 2026-04-21 第三方听歌软件无感 P2P 兼容层可行性调研任务单

## 当前问题定义

- 这次要解决的问题，不是继续改当前用户端或服务端界面。
- 当前目标是评估：
  - `第三方听歌软件`
  - `第三方云盘 / 音乐服务`
  - `现有 Cloud Relay + P2P 体系`
- 能否在**不修改第三方应用源码**或**尽量少侵入第三方应用**的前提下，让第三方听歌软件在访问音乐资源时优先走 P2P，而不是继续走公网 HTTPS。

更准确地说，这次不是问“我们自己的用户端能不能开音乐工作台”，而是问：

- 第三方播放器是否可以继续按它原本的使用方式工作；
- 但它访问到的音乐流、封面、下载流量，能否被本地兼容层自动改写为 P2P 获取；
- 从而避免大量音频流量继续经过云端公网入口。

## 核心目标

服务端 Codex 这次只做一件事：

- 调研“第三方听歌软件无感 P2P 接入”是否可行，并给出最推荐的技术路径。

这里的“无感”指：

- 用户最好继续使用原本的第三方听歌软件；
- 不要求用户手工复制每一首歌的 P2P 地址；
- 系统应尽量自动完成：
  - 服务发现
  - 节点发现
  - 鉴权沿用
  - 数据面切换到 P2P

## 非目标

这次先不要做下面这些事：

- 不要直接开始开发。
- 不要先改当前用户端或服务端代码。
- 不要先承诺一定能支持所有第三方播放器。
- 不要先做移动端真机打包。
- 不要把“现有用户端能开 P2P 工作台”当成这次问题的答案。

## 真实要回答的问题

服务端这次必须回答清楚下面这些问题：

### 1. 是否能不改第三方应用源码

- 如果第三方软件支持自定义服务器地址、标准协议或插件机制，是否可直接接入。
- 如果第三方软件不支持插件，是否还能通过本地透明兼容层实现。
- 如果第三方软件依赖固定公网域名或固定 HTTPS，是否仍有办法劫持到本地 P2P 网关。

### 2. 数据面是否能与控制面分离

- 登录、鉴权、服务发现是否继续走云端。
- 歌曲流、封面、Range 请求、断点续传、Seek 是否可切到 P2P。
- 当 P2P 不可达时，是否可安全回退到公网 HTTPS。

### 3. 本地兼容层需要做到什么程度

至少要判断下面哪条路可行：

- 直接把第三方软件的服务器地址改成 P2P 地址。
- 保持第三方软件连接原有域名，但用本地 `localhost` 网关做代理和重写。
- 用系统级 HTTP/HTTPS 代理实现透明改写。
- 用 TUN/VPN/虚拟网卡方式把目标域名劫持到本地兼容层。
- 以上都不稳，不建议做。

### 4. 不同平台的可行性差异

必须分开评估：

- Windows
- macOS
- Android
- iOS

不能把桌面端能做就等同于移动端也能做。

## 必须重点调研的技术点

服务端调研时重点盯下面这些点，不要泛泛而谈。

### 1. 第三方客户端协议类型

要先确定目标播放器 / 客户端到底使用哪类协议：

- WebDAV
- Subsonic / OpenSubsonic
- Jellyfin / Emby
- Navidrome API
- 直链 HTTP / HTTPS
- 自有私有协议
- 其他

### 2. 是否支持自定义服务器

- 是否允许手工填写服务端地址。
- 是否允许填写自定义 Host / Base URL / Path Prefix。
- 是否支持插件、脚本、扩展。
- 是否会强依赖固定官方域名。

### 3. HTTP 兼容性要求

必须判断第三方软件是否依赖下面这些行为：

- `Range` 请求
- 长连接
- 流式播放
- Seek / 快进 / 快退
- 封面懒加载
- 分块下载
- ETag / Last-Modified / Cache-Control
- 302 / 307 跳转
- Cookie / Bearer Token / 自定义签名

### 4. HTTPS 与证书风险

这是高风险点，必须单独判断：

- 是否能接受改成 `http://127.0.0.1:xxxx`
- 是否必须是 `https://域名`
- 是否做证书校验增强
- 是否可能存在 certificate pinning
- 是否可能走 QUIC / HTTP3

### 5. 本地透明接管难度

如果第三方软件不能直接改目标地址，要判断是否能通过下面方式接管：

- hosts / 本地 DNS
- 本地反向代理
- 系统代理
- TUN / VPN
- 虚拟网卡

并判断每种方式在不同平台上的成本和稳定性。

## 当前推荐的调研方向

服务端要优先判断下面这条路线是否成立：

1. 第三方软件继续连接一个“看起来兼容原服务”的本地地址。
2. 本地兼容层接住第三方软件的请求。
3. 控制面请求仍然转到云端入口。
4. 真正的大流量媒体请求改写为服务节点 P2P 地址。
5. P2P 失败时再回退到公网 HTTPS。

也就是说，这次重点不是“把 P2P 硬塞进第三方软件内部”，而是判断：

- 能否在第三方软件外面包一层本地兼容层；
- 让第三方软件误以为自己还在访问原服务；
- 实际数据面已经被本地层导向 P2P。

## 服务端输出要求

服务端最后不要只给一句“可行 / 不可行”。

必须按下面结构输出：

### 1. 目标软件画像

- 第三方听歌软件名称
- 版本
- 平台
- 第三方云盘 / 音乐服务名称
- 版本
- 当前接入协议

### 2. 协议与流量路径拆解

- 哪些请求属于登录 / 鉴权 / 服务发现
- 哪些请求属于歌曲流 / 封面 / 下载
- 哪些请求理论上可切 P2P
- 哪些请求必须保留云端

### 3. 可行性分级

每个目标软件都要给出以下四档之一：

- `A. 可直接改为 P2P 地址`
- `B. 可通过本地 localhost 网关实现`
- `C. 只能通过系统级代理 / TUN / VPN 实现`
- `D. 成本过高，不建议做`

### 4. 平台差异

- Windows 可行性
- macOS 可行性
- Android 可行性
- iOS 可行性

### 5. 风险列表

至少列出：

- 协议兼容风险
- 证书 / HTTPS 风险
- 播放器升级后失效风险
- 移动端系统限制
- 性能与缓存风险
- 调试复杂度

### 6. 最推荐方案

只能给一个主推荐路线，说明：

- 为什么推荐它
- 为什么不推荐其他路线
- 第一步最小验证应怎么做

## 第一阶段只做调研，不做开发

服务端这轮交付只接受：

- 文档调研
- 协议分析
- 风险判断
- PoC 路线建议

不接受：

- 直接大规模写代码
- 直接承诺全平台支持
- 在没有确认第三方协议前就开工做本地透明代理

## 如果信息不足，服务端必须先反向收集

如果当前还缺少下面这些信息，服务端要先明确缺口，而不是硬猜：

- 具体第三方听歌软件名称
- 软件版本
- 运行平台
- 具体第三方云盘 / 音乐服务名称
- 当前接入方式
- 当前歌曲实际播放 URL 形态
- 是否可抓包 / DevTools / 日志

## 验收标准

这次调研完成后，至少要达到下面标准：

- 我能明确知道这事在 PC 上是否值得做。
- 我能明确知道移动端是否值得单独推进。
- 我能明确知道核心难点在：
  - 第三方协议
  - HTTPS / 证书
  - 本地透明代理
  - 系统级网络接管
  - 还是其他地方
- 我能明确知道下一步应该先做哪一个最小 PoC。

## 当前结论预期

服务端最后的结论必须尽量收敛到这种形式：

- `桌面端建议推进 / 不建议推进`
- `移动端建议推进 / 不建议推进`
- `首选路线是本地 localhost 网关 / 系统代理 / TUN-VPN / 直接改服务器地址`
- `建议先验证的软件组合是 XXX + XXX`

不要只给大而空的“理论上可以”。
